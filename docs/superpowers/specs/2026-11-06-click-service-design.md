# Click Service — Design

**Date:** 2026-11-06
**Status:** Approved

## Intent

The click service is the entry point of the ad click aggregator (see `docs/architecture.png`). It
receives ad clicks over HTTP and publishes each one as an event to Kafka, where the aggregation
service (`stream-processor`) will later consume them and build 1-minute counts per ad.

This first version establishes the ingestion path only: receive a click, publish it durably, answer
the caller. It is also the first real service in the repository, so it sets the pattern (Spring Boot,
hexagonal architecture) the other services are expected to follow.

## Goals

- `POST /click` endpoint that accepts an `adId`, publishes a click event to Kafka and responds 2xx.
- The 2xx response is only sent after Kafka has acknowledged the write, so an accepted click is never
  lost. If publishing fails, the caller gets an error and can retry.
- Full hexagonal architecture (ports and adapters).
- Unit tests for the Kafka publishing adapter.

## Non-Goals (this version)

- **Redirect** to the advertiser's website. Deferred; the endpoint just answers 2xx.
- **Integration tests with Testcontainers.** Planned for a later session.
- **Client-side idempotency** (a click id or signed impression id sent by the caller). The request
  carries only `adId`, so a browser re-sending the same click cannot be detected yet.
- Docker Compose / local Kafka infrastructure, the bootstrap script, authentication, rate limiting,
  observability beyond Spring Boot defaults (see the Scope section of the README).

## Decisions

### Decided by the user

- **Module name:** the module is renamed from `services/click-processor` to `services/click-service`.
  The architecture diagram's naming wins over the Hello Interview article's.
- **Framework:** Spring Boot.
- **Architecture:** full hexagonal — domain, application (inbound and outbound ports, use case
  implementation) and adapters (web in, Kafka out), with mapping between layers.
- **Request:** the body contains only `adId`.
- **Event fields:** the service builds the event with:
  - `adId` — from the request;
  - `clickId` — a UUID generated by the service, giving each event a stable identity so the
    aggregator can deduplicate re-deliveries from Kafka;
  - `timestamp` — the instant the service received the click; the aggregator uses it to bucket
    clicks into minutes.
- **Durability:** respond only after Kafka acknowledges the write, with `acks=all`.
- **Partitioning:** the Kafka message key is `adId`, as in the diagram.
- **Contract:** `ClickEvent` in `libs/click-event` is the wire contract published to the topic and
  shared with `stream-processor`. Its placeholder class gets the three fields above.
- **Tests:** unit tests only for this version, focused on the Kafka production.
- **Topic ownership:** the click service declares the `click-events` topic itself at startup (a
  Spring `NewTopic` bean), with partitions and replication factor configurable. Defaults: **12
  partitions** and replication factor **1** (a single local broker). Topic creation may move to the
  infrastructure (Docker Compose) once it exists.

### Calls made by Claude (open to review)

- **Package:** `com.wmbatista.adclick.clickservice`.
- **Endpoint contract:**
  - Request: `POST /click`, `Content-Type: application/json`, body `{"adId": "<string>"}`.
    `adId` is an opaque non-blank string.
  - Success: `202 Accepted` with an empty body. 202 rather than 200 because the click is durably
    stored but not yet counted — aggregation happens asynchronously.
  - Missing, null or blank `adId` (or a malformed body): `400 Bad Request`.
  - Kafka publish fails or times out: `503 Service Unavailable`, signalling the caller to retry.
- **Topic:** `click-events`, configurable through application properties.
- **Serialization:** `ClickEvent` serialized as JSON; `timestamp` as ISO-8601 UTC instant;
  `clickId` as a UUID string. Key serialized as a plain string.
- **Producer configuration:** `acks=all`, `enable.idempotence=true` (prevents duplicates from the
  producer's own retries). Bootstrap servers default to `localhost:9092`, overridable by environment
  variable.
- **Blocking send:** the use case waits for the Kafka acknowledgement with a bounded timeout
  (configurable, default a few seconds). Spring virtual threads are enabled
  (`spring.threads.virtual.enabled=true`) so waiting requests don't exhaust a platform thread pool
  at 10k clicks/s.
- **No "503 but written anyway":** the Kafka producer keeps retrying until `delivery.timeout.ms`
  (default 120s), so a request could time out with 503 while the record still lands later; the
  caller's retry would then get a new `clickId` and the click would be counted twice. To avoid
  this, the producer's `delivery.timeout.ms` (which must be ≥ `linger.ms` + `request.timeout.ms`)
  is set no higher than the use case's wait timeout, so Kafka settles the send before the HTTP
  response is chosen. The service refuses to start if the configured values break this, and a unit
  test pins the packaged defaults. This **narrows** the window but cannot close it: when
  `delivery.timeout.ms` expires on the client, the broker may already have appended (or may still
  append) the record, so a rare 503 can still be followed by a write. Fully preventing that double
  count needs a client-supplied idempotency key, which is a non-goal of this version.
- **Testability seams:** the current time comes from an injected `java.time.Clock` and the click id
  from an injected id generator, so the use case is deterministic in tests.
- **Mocking library:** MockK (idiomatic for Kotlin), added to the version catalog.
- **Extra unit tests:** besides the Kafka adapter, the use case also gets unit tests (with a fake
  outbound port). They are cheap and pin down the event-building logic.

## Architecture

```
services/click-service/src/main/kotlin/com/wmbatista/adclick/clickservice/
├── ClickServiceApplication.kt          # @SpringBootApplication entry point
├── domain/
│   └── Click.kt                        # domain model: clickId, adId, timestamp
├── application/
│   ├── port/in/RegisterClickUseCase.kt # inbound port: register(adId)
│   ├── port/out/PublishClickPort.kt    # outbound port: publish(click)
│   └── service/RegisterClickService.kt # implements the use case: builds Click, calls the port
├── adapter/
│   ├── in/web/
│   │   ├── ClickController.kt          # POST /click → RegisterClickUseCase
│   │   ├── ClickRequest.kt             # request DTO
│   │   └── ...                         # error handling (400 / 503)
│   └── out/kafka/
│       ├── KafkaClickPublisher.kt      # implements PublishClickPort via KafkaTemplate
│       └── ClickEventMapper.kt         # Click (domain) → ClickEvent (wire contract)
└── config/                             # wiring: Clock, id generator, Kafka producer/topic
```

Note: `in` is a Kotlin keyword, so the package segment must be written with backticks or the
builder may choose another name (e.g. `inbound`/`outbound`).

Flow:

1. `ClickController` validates the request and calls `RegisterClickUseCase.register(adId)`.
2. `RegisterClickService` builds a `Click` with a fresh `clickId` and the current `timestamp`, and
   calls `PublishClickPort.publish(click)`.
3. `KafkaClickPublisher` maps `Click` to `ClickEvent`, sends it to the topic keyed by `adId` and
   waits for the acknowledgement. Failures and timeouts surface as a domain/application exception.
4. The controller answers 202, or 503 if publishing failed.

The domain and application layers have no Spring or Kafka dependencies.

## Build Changes

- Add Spring Boot (web, Kafka, validation as needed), the Kotlin Spring plugin and MockK to
  `gradle/libs.versions.toml`. Use the latest stable Spring Boot release compatible with Kotlin 2.4
  and JDK 25.
- Rename the module directory and its entry in `settings.gradle.kts`; replace the placeholder
  `Main.kt` with the Spring Boot application.
- `libs/click-event` gets the three fields. It needs no serialization framework dependency unless
  the builder finds one necessary for JSON round-tripping (e.g. Jackson Kotlin module on the service
  side).
- Update the README: module name in the architecture table and repository layout, and the
  `./gradlew :services:click-processor:run` example.

## Testing

- **`KafkaClickPublisher` (required):** with a mocked `KafkaTemplate`, verify the topic, that the key
  is `adId`, that the payload carries `clickId`, `adId` and `timestamp` correctly, and that a failed
  or timed-out send surfaces as the publishing exception.
- **`RegisterClickService`:** with a fixed `Clock`, a fixed id generator and a fake
  `PublishClickPort`, verify the built `Click` and that publishing errors propagate.
- `./gradlew build` must pass.

## Left to the Builder

- Whether Spring configuration lives in the module's build script or in a new convention plugin

- Exact error-handling mechanism in the web adapter (`@ControllerAdvice` or similar).
- Exact names of the `in`/`out` adapter packages, given the Kotlin keyword issue.
